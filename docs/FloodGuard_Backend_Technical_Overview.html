1. Purpose and Scope

FloodGuard AI is a backend for flood-condition monitoring, national district screening, risk inference, prediction history, operational state, incidents, citizen reports, emergency resources, and downstream automation context. It exposes versioned REST APIs under /api/v1.

Live national weather batches + station river discharge → district screening and detailed XGBoost risk → cached GIS layer + persisted predictions and events

Weather normalization

The live provider requests hourly precipitation, temperature, relative humidity, and 0-7 cm soil moisture. It calculates current, previous 1/6/24-hour, and forecast 6/24-hour rainfall totals.

River normalization

The live river provider uses GloFAS daily modeled discharge at configured river coordinates. It returns current discharge, daily change, next-day forecast, and a simple rising/normal status.

River-level constraint: GloFAS provides modeled discharge, not measured gauge height. Live responses therefore return level-related fields as null. FloodGuard does not fabricate a water level.

Synthetic development dataset

The generator in app/ml/synthetic_data.py remains only for development and regression tests:

  • Rainfall, river conditions, discharge, discharge change, and soil moisture are sampled from bounded synthetic ranges.
  • Discharge is correlated with synthetic river level; discharge change is correlated with synthetic rise rate.
  • The probability label is a weighted hydrometeorological score plus a high-rain/high-river interaction and small random noise.
  • 35% of rows have level-related inputs removed to train the model to operate when only discharge is available.

This synthetic artifact is disabled by default with ML_MODEL_ENABLED=false.

Failure policy

Production uses ALLOW_RULE_BASED_FALLBACK=false. If the enabled ML artifact is missing, corrupt, or fails inference, the API returns structured HTTP 503 instead of silently changing models. A rule-based fallback can be enabled deliberately for a separate degraded-mode deployment. Provider failures never substitute simulation data and return structured HTTP 502.

Production also defaults to ML_MODEL_ENABLED=false because the bundled XGBoost artifact is trained on synthetic development data. In this mode rule_based_v1 is the declared primary model operating on live inputs, not a silent fallback. Enable the bundled artifact only for development, or replace it with a historically trained and validated artifact before operational ML use.

Real-data research run

The classifier uses binary:logistic, depth 3, learning rate 0.04, row subsampling 0.85, column subsampling 0.90, early stopping, and seed 42. Two independent holdouts are required:

Event holdout keeps complete events in one split only. Geographic holdout assigns all rows in each 2-degree latitude/longitude block to one split only; 15 geographic blocks are represented. This tests transfer to unseen areas.

Promotion requires both holdouts to achieve ROC-AUC at least 0.75, precision at least 0.60, and recall at least 0.60. The model failed. Ordinary accuracy is not accepted by itself because majority non-flood predictions can inflate it. Status is rejected_holdout_quality, deployment_eligible=false, and production remains on rule_based_v1.

Full provenance, exact split membership, metrics, limitations, and acceptance gates are stored in app/ml/artifacts/flood_risk_xgboost_real.model-card.json.

DesInventar district-date research run

The second experiment uses the official UNDRR DesInventar Pakistan export. The cleaning pipeline keeps FLOOD and FLASH FLOOD, validates dates from 2000 onward, applies explicit historical district aliases, rejects unknown districts, and deduplicates district-date labels. It produced 1,704 cleaned positive district-dates from 2,912 raw flood records. Year 2007 was excluded completely from model rows because the free historical provider quota ended before national covariate coverage was complete; excluding the whole year avoids partial-district selection bias.

Conclusion: XGBoost capacity and tuning are not the main blocker. Geographic transfer remains weak because district representative points do not describe full catchments, DesInventar is an impact-reporting catalogue rather than continuous inundation truth, and measured gauge levels, station thresholds, catchment rainfall, terrain slope, river distance, drainage capacity, and flood-protection context are absent. Recommended next data work is authority gauge integration, catchment/raster aggregation, static susceptibility layers, and event-based geographic backtesting before another promotion decision.

Declared partial-coverage experiment

A smaller model was tested rather than assuming national coverage. The Lower Indus pilot was fixed before evaluation as six contiguous blocks covering Badin, Barkhan, Dadu, Ghotki, Hyderabad, Jacobabad, Jafarabad, Jhal Magsi, Kachhi, Kalat, Khuzdar, Kohlu, Lasbela, Mastung, Nasirabad, Sibi, Thatta, and Umerkot. The dataset contains 4,597 rows and 652 positive district-dates.

6. National GIS Screening

The endpoint GET /api/v1/gis/national-risk returns a GeoJSON FeatureCollection covering 126 Pakistan ADM2 district geometries. The packaged simplified boundaries are from geoBoundaries PAK ADM2 (2019), distributed as public-domain data. The optional bbox=west,south,east,north parameter filters output to a map viewport.

9. Known Limitations and Next Production Steps

  1. Obtain quality-controlled gauge observations, official station warning thresholds, and verified flood extents/outcomes from FFD, WAPDA, NDMA, or provincial authorities.
  2. Add catchment-average rainfall, terrain slope/elevation distribution, river distance, drainage, land cover, and flood-protection features.
  3. Integrate authorized FFD/WAPDA gauge observations and station-specific flood thresholds.
  4. Use station-specific rating curves only when validated; never convert discharge to level with a generic formula.
  5. Replace the 2019 public-domain demonstration boundaries with NDMA-authorized current administrative boundaries.
  6. Add provider retry/backoff, detailed-location caching, dependency-aware health checks, and production database migrations.
  7. Move high-volume historical GIS observations to PostGIS and vector/raster tiles as data density grows.
  8. Verify and routinely update static emergency-resource records.
